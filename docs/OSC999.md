# OSC 999:子进程命令信道(协议规范)

> 请求里那条**命令串**的完整语法与全部命令见 [SCRIPT.md](SCRIPT.md);
> 本文件只讲**信道**(怎么发、怎么回、谁能发、字节怎么编码)。

> CETerm 的对外控制序列手册(本协议部分)。
> 实现落点:`src/canvas/vt.odin`(信道层)、`src/canvas/commandpipe.odin`(管道)、
> `src/command/execute.odin`(ret 内容)。回归:`playground/osccmdtest/`。

---

## 0. 一句话

程序把自己的 **stdout** 当作指令入口(经 OSC 999 发一条命令),CETerm 执行后把
**ret** 写回程序的 **stdin**。CETerm 自身的命令栏、配置文件、本信道共用同一套
指令语义与同一个解释器 —— **只有载体不同**。

```
程序 stdout ──OSC 999 请求──► vtparse 状态机 ──► Console 的命令信道 ──► command 解释器
                                                                          │ 下一帧
程序 stdin  ◄──ConPTY 输入── 信道编码(转义 + 信封) ◄── ret(状态 + 文本) ┘
```

---

## 1. 三条硬约束(协议为什么长这样)

这三条都不是设计偏好,是**从实现里读出来的事实**;协议的形状由它们决定。

### 1.1 请求只能是单行可打印

OSC 载荷经 `tr_osc_string` 状态机(`src/canvas/vtparse.odin`):

| 字节 | 行为 | 后果 |
| --- | --- | --- |
| `0x20-0x7F` | `OscPut` | 收进载荷 |
| 合法 UTF-8 多字节序列 | `OscPut`(逐 rune 重编码) | 收进载荷 |
| `0x00-0x17`、`0x19`、`0x1C-0x1F` | **`.Ignore`** | **静默消失**,不报错 |
| `0x07`(BEL) | 终止 OSC | 载荷到此为止 |
| `0x18`/`0x1A`(CAN/SUB) | Execute + 回 Ground | **直接截断** |
| `0x1B`(ESC) | 走 ST 终止路径 | 终止 |

⇒ **请求必须单行**。放 `\n` 不会报错,会无声消失;放 CAN/SUB 会截断。

### 1.2 应答写进的是 stdin,而 stdin 是**键盘输入流**

每个字节都是一次"按键"。放行控制字节 = CETerm 替攻击者按键:

| 字节 | 在 shell 里的含义 |
| --- | --- |
| `0A` `\n` | **回车 —— 执行当前命令行** |
| `0D` `\r` | 同 |
| `03` | **Ctrl-C(SIGINT)** |
| `04` | **EOF** |
| `1A` | Ctrl-Z(SIGTSTP) |
| `7F` | 退格 |
| `1B` | 转义序列起始(能伪造别的键) |

⇒ 应答的 body **硬保证只含 `0x20-0x7E` 与 `0x80-0xFF`(UTF-8)**。这是
`OscCmdEncode` 的唯一职责,也是全协议**唯一不可协商的不变式**(见 §7)。

### 1.3 指令不能在解析当帧同步执行

OSC 处理发生在 `ConsoleUpdateTree` 的遍历里(正在解析该会话的输出)。若就地
`ExecuteCommand`,那么 `split`/`destroy` 这类命令**会改正在被遍历的那棵树** ——
遍历中改容器;而且会让 canvas 绕过 `command` 这个唯一解释器。

⇒ 请求只**入队**(`PushCommand`),执行在**下一帧**的 `command.Update()`。
这不是为了统一才走的管线,是**必须**异步。

### 1.4 顺带的收益:回声环路熔断

应答可能被对端程序**回显**(最典型:`cat`;或 conhost 开着 `ENABLE_ECHO_INPUT`),
那串字节出现在程序输出里就会**再被解析成一条请求** → 无限循环。
所以应答带方向标记 `>`(见 §3.3),CETerm 见到 `>` 开头的载荷一律丢弃。

## 2. 请求序列(程序 → CETerm)

```
ESC ] 999 ; [标记] <命令串> ST
```

| 成分 | 字节 | 说明 |
| --- | --- | --- |
| 引入 | `1B 5D 39 39 39 3B` | `ESC ] 999 ;` |
| 标记 | `2D`(`-`)或省略 | `-` = **no-ret**;省略 = **on-ret**(缺省) |
| 命令串 | UTF-8 | 与命令栏**完全同语法**(见 §2.2) |
| 终止 | `1B 5C`(`ESC \`)或 `07`(BEL) | 两种都接受 |

### 2.1 字节级示例

```
on-ret(缺省):查询工作目录
  1B 5D 39 39 39 3B 63 77 64 1B 5C
  ESC ]  9  9  9  ;  c  w  d  ESC \

no-ret:切分窗口,不要返回
  1B 5D 39 39 39 3B 2D 73 70 6C 69 74 20 72 69 67 68 74 1B 5C
  ESC ]  9  9  9  ;  -  s  p  l  i  t  ␠  r  i  g  h  t  ESC \
```

### 2.2 命令串语法

与命令栏、配置文件**同一个解析器**(`ParseCommandStringEx`):

- 「命令名 参数… `@id`」,大小写不敏感
- 字符串参数用 `"..."` 包裹(串内不能含引号)
- 末尾 `@id` 指定目标窗格(仅窗口类命令接受),缺省 = 当前焦点
- 键位类参数形如 `alt+shift+l`

可用命令清单 = `help`;单条说明 = `help <命令>`。

### 2.2b `feed` 的参数额外支持转义(其余命令保持字面)

| 写法 | 字节 | 用途 |
| --- | --- | --- |
| `\r` | `0D` | **回车** |
| `\n` | `0A` | 换行 |
| `\t` | `09` | 制表 |
| `\e` | `1B` | ESC |
| `\\` | `5C` | 反斜杠 |
| `\0` | `00` | NUL |
| `\xNN` | 任意 | 两位十六进制:`\x22` = `"`、`\x03` = Ctrl-C |

- **为什么只有 `feed`**:OSC 载荷**物理上带不了控制字节**(§1.1 的状态机把 `00-1F`
  一律 Ignore,`\r` 会被静默吞掉),而 `feed` 正是"注入原始按键"的命令 ——
  没有转义就根本发不出回车。其余命令的字符串必须保持字面,否则 `cwd "C:\Users"`
  这类路径会被吃掉反斜杠。
- **`"` 也没法直接写**:命令语法规定串内不能含引号,所以打引号用 `\x22`。
- **未知转义原样保留**(`C:\Users` 原样通过),路径类文本不会出意外。
- **装不下即失败**,不静默截断。

### 2.3 长度与边界

| 边界 | 值 | 超限行为 |
| --- | --- | --- |
| OSC 载荷缓冲 | 4096(`OSC_BUFFER`) | **整段作废**(`osc_bad`),**不回复** |
| 命令串上限 | 512(`MAX_POLL_TEXT`) | **拒收**,回一条 `>err;请求过长` |
| 单条 token 上限 | 24(`MAX_CMD_TOKENS`) | 解析期报错 → 回 `>err;参数过多` |

前两条是"拒收优于截断":截断一条命令 = **执行了另一条命令**。

### 2.4 被丢弃的载荷

| 情形 | 行为 |
| --- | --- |
| 空载荷 | 丢弃 |
| 首字节是 `>` | 丢弃(这是应答的回声,见 §1.4) |
| 未授权(见 §8) | 丢弃,**不回复** |
| 无会话(工具 console) | 丢弃(没有子进程可回) |

## 3. 应答序列(CETerm → 程序)

```
ESC ] 999 ; > <状态> ; <body> ST
```

| 字段 | 字节 | 取值 |
| --- | --- | --- |
| 引入 | `1B 5D 39 39 39 3B` | `ESC ] 999 ;` |
| **方向标记** | `3E`(`>`) | **恒为 `>`** |
| 状态 | — | `ok` / `err` |
| 分隔 | `3B`(`;`) | |
| body | 转义后 | 单行、纯可打印;无值 = `?`(`3F`) |
| 终止 | `1B 5C` | `ESC \` |

**头部恒为 3 段,body = 第二个 `;` 之后的全部字节。** 所以 body 里的 `;`
和 `\` 都不需要转义 —— 子进程按「切开前两个 `;`,剩下都是 body」解析即可。

### 3.1 状态表

| 状态 | 含义 | body |
| --- | --- | --- |
| `ok` | 执行成功 | 有值 = 查询回显;无值 = `?` |
| `err` | 执行失败或请求被拒 | 失败原因(**必非空**) |

### 3.2 字节级示例

```
有值
  ESC ] 999 ; > ok ; C:\Users
  1B 5D 39 39 39 3B 3E 6F 6B 3B 43 3A 5C 55 73 65 72 73 1B 5C

成功但无值(占位符)
  ESC ] 999 ; > ok ; ?
  1B 5D 39 39 39 3B 3E 6F 6B 3B 3F 1B 5C

失败
  ESC ] 999 ; > err ; 未知命令: xyz
  1B 5D 39 39 39 3B 3E 65 72 72 3B ...

no-ret(请求带 '-' 前缀)
  —— 不写任何字节
```

注意上例中路径的 `\`(`5C`)是**裸的**:终止符是**两字节** `1B 5C`,
单个 `5C` 只是普通载荷字节,子进程按 `ESC \` 扫描即可。

### 3.3 方向标记 `>` 的两个作用

1. **环路熔断**:应答若被对端回显/打印,CETerm 见到 `>` 开头即丢弃(§1.4)。
   合法命令串不以 `>` 开头,零歧义。
2. **重同步**:请求与应答共用号码 999,配对靠定序(§4)。若子进程少读一条导致
   错位,它可以扫 `ESC ] 999 ; >` 重新对齐,而不必错到底。

> **与早期草案的差异**:`DESIGN.md` 早先记过「OSC 998 回执」的想法(用另一个号码
> 承载应答)。落地采用**同一号码 + `>` 前缀**,理由:一个号码 = 一条代码路径;
> 且 `>` 同时兼任熔断器,而"另一个号码"做不到熔断(未授权的程序照样能发 998)。

## 4. 定序与配对

- **一个请求恰好一条应答**(on-ret);**no-ret 请求恰好零条**。
  ⇒ 子进程可以严格「发 N 读 N」,不需要请求 id。
- **严格 FIFO**:同一窗格的应答按请求顺序回写。这是免费的 ——
  命令管道本身是单写者队列,`ReapCommand` 单调推进游标。
- **延迟约 1 帧(≈16ms)**:请求在解析帧入队,下一帧开头执行,同帧稍后回写。
  子进程侧请用 `read -t 1` 这类**宽松超时**,不要用毫秒级。

> 为什么不用"ret 为空 = 无返回"来省掉状态字段:on-ret 却**没有返回值**的命令
> 也产生空 ret,两者会撞在一起。所以由 `ret_status` 三态区分(§5),
> 空串只表示"内容为空"。

## 5. ret 的三态

`CommandEvent.ret_status`(`src/canvas/commandpipe.odin`):

| 状态 | 含义 | 信道行为 |
| --- | --- | --- |
| `None` | **不产生 ret**(请求标了 no-ret) | **一个字节都不写** |
| `Ok` | 成功 | 写;body 空则用占位符 `?` |
| `Err` | 失败 | 写;body 必非空(失败原因) |

**不变式:`None` ⟹ `ret_len == 0`。** 即消费者只看状态就够,不必再看内容长度。

### 5.1 no-ret 标记

`-` 前缀是**通用**的:命令栏里敲 `-split right`、配置文件里写 `-vsync on`、
OSC 请求里发 `-count` 语义相同 —— 都表示"执行它,但不要回显/不要返回"。
标记由 `command` 层剥除(`NO_RET_MARK`),canvas 不认识它。

### 5.2 占位符 `?`

on-ret 且命令无返回值时,body 为单个 `?`。作用是**让字段数恒定**(永远是 3 段),
子进程不必处理变长形状。

`?` 同时是 `help` 的别名(输入方向),但方向不同、位置不同(它在 `> ok ;` 之后),
不会混淆。

## 6. 授权模型

### 6.1 授权 = 给该窗格建一条命令信道

**没有独立的"已授权"字段**;`Console.poll_h` 非 0 即已授权,为 0 即不认 999。
状态就在句柄里。

| 操作 | 命令 |
| --- | --- |
| 授权焦点窗格 | `osc on` |
| 授权指定窗格 | `osc on @3` |
| 撤销 | `osc off` |
| 翻转 | `osc`(无参数) |

授权**有意只走命令栏**,配置文件里没有为它绑按键 —— 一次误触就等于把完整命令
能力交给那个窗格里的程序。

### 6.2 生命周期:换程序必然重新授权

授权在**会话初始化**时重置,而 `consoleInitSession` 是"这个 console 里开始了
一个新程序"的**唯一入口**(`CreateConsole` 与 `consoleStartSession` 都走它),
所以这条是结构保证的,没有路径能绕过:

| 路径 | 行为 |
| --- | --- |
| `consoleInitSession`(重开/新开会话) | 释放 poll → 新程序**未授权** |
| `consoleClearSession`(清空会话) | 释放 poll |
| `DestroyConsole`(销毁窗格) | 释放 poll |

### 6.3 容量

`MAX_COMMAND_POLLS = 32`(槽 0 保留 → 31 可用);命令栏自占 1。
⇒ **最多 30 个窗格可同时授权**。池满时 `osc on` 失败(命令栏会打出失败原因)。

### 6.4 授权 = 完整信任(重要)

本协议**不做按命令分级**。授权之后,那个窗格里的程序获得 CETerm 的**完整命令
能力**,包括:

| 命令 | 能力 |
| --- | --- |
| `launch <cmd>` | 起任意进程 |
| `load <path>` | 执行任意配置文件(等价于任意命令) |
| `bgshader <path>` | 读任意文件 + 编译着色器 |
| `bind` / `unbind` | 重绑用户键位 |
| `feed` | 往**别的会话**注入输入 |
| `paste` | **把用户剪贴板灌进自己的 stdin 再读走**(剪贴板外泄) |

这是**明确的设计选择**(用户在场、从命令栏显式授予、按窗格记忆),不是缺陷。
**未授权时信道完全静默**:不执行、不回复 —— 未授权的程序连一个字节都塞不进
用户的 stdin,也无从探测信道是否存在。

> 若将来要"信道开着但某些命令仍不给程序用",正确做法是把策略挂在
> **poll(信道)**上而不是事件上 —— 否则就是往命令解释器里塞"来源"信息。
> 现状刻意不做。

## 7. 信道编码(唯一防注入守卫)

`OscCmdEncode(status, body, out)`(`src/canvas/vt.odin`)是**唯一**把 ret 变成
字节的地方。它的输出保证落在 `0x20-0x7E ∪ 0x80-0xFF`。

### 7.1 转义表

| 原字节 | 输出 | 理由 |
| --- | --- | --- |
| `5C` `\` | `5C 5C`(`\\`) | 反转义需要,否则与下一行歧义 |
| `0A` | `5C 6E`(`\n`) | 否则 shell 当回车**执行** |
| `0D` | `5C 72`(`\r`) | 同 |
| `09` | `5C 74`(`\t`) | 制表符会移动光标 |
| 其余 `00-1F` | **丢弃** | 含 `1B`(可伪造序列)、`07`(BEL)、`03`/`04`(信号/EOF) |
| `7F`(DEL) | **丢弃** | 退格 |
| `20-7E` | 原样 | |
| `80-FF` | **原样** | UTF-8 多字节字符(中文等),无控制语义 |

### 7.2 截断规则

**截 body,绝不截 framing。** body 超过缓冲上界时,在保留的末尾追加
`[truncated]`(`OSC_CMD_TRUNC`)作为标记。半条序列会让对端的解析器卡死,
所以终止符 `ESC \` 永远完整写出。

### 7.3 不可打印字节不是内容

丢弃它们**不是有损压缩**,而是**语义正确**:控制字节在 stdin 上不是"字符",
是"按键"。子进程如果需要原样文本,读的就是它自己程序输出的文本,不是这条 ret。

## 8. 完整往返示例

### 8.1 请求"当前工作目录"

程序侧(C 风格伪码,展示字节语义):

```c
// 1) 发请求:写到自己的 stdout
write(1, "\x1b]999;cwd\x1b\\", 11);

// 2) 读应答:从 stdin 读到 ESC \ 为止
char buf[512]; int n = 0, c;
while ((c = read(0, &buf[n], 1)) == 1) {
    if (n >= 1 && buf[n-1] == 0x1b && buf[n] == '\\') break;
    if (++n == sizeof(buf)) break;
}
// buf 形如: "\x1b]999;>ok;C:\\Users\\GroupTheory\x1b\\"
```

shell 里发一条(单引号包裹,避免历史展开等意外):

```sh
printf '\033]999;cwd\033\\'          # 请求 → stdout
```

> **注意**:应答进的是 **stdin**,而交互式 shell 的 stdin 同时是命令行。
> 所以本信道是给**自己读 stdin 的程序**用的,不是给 shell 一行流用的 ——
> 交互 shell 里发完不读,应答会被下一个提示符吃掉,表现为"终端往命令行里塞了
> 一串转义序列"。这和 CPR/DA/OSC 52 查询是同一条纪律。

### 8.2 一次 no-ret 控制

```sh
printf '\033]999;-split right\033\\'   # 切分,不问结果;stdin 上不会有任何回应
```

### 8.3 从命令栏授权

```
F2 → osc on            # 授权焦点窗格
F2 → osc on @3         # 授权 3 号窗格
F2 → osc off           # 撤销
F2 → osc               # 翻转
```

成功时命令栏回显 `osc 信道: on` / `off`。

### 8.4 演示:让终端自己打字

`playground/oscsailor/main.odin` —— 一个**只往 stdout 打字节**的程序。在 CETerm 里
跑起来时它反过来驱动 CETerm:切出一个窗格,往里面一个字一个字地敲出
`print "Hello, Sailor!"` 再敲回车。全部请求都是 **no-ret**,所以它只写不读。

```sh
# 在 CETerm 的某个窗格里:
# 1) F2 → osc on              授权本窗格(未授权时 999 被静默忽略)
# 2) odin run playground/oscsailor/
```

它实际打出的 24 条请求(实测捕获):

```
 1: split right
 2..23: feed "p" feed "r" feed "i" feed "n" feed "t" feed " "
        feed "\x22"  feed "H" ... feed "r" feed "!" feed "\x22"
24: feed "\r"
```

数据全程:`本程序 stdout → ConPTY → CETerm 的 OSC 解析器 → 命令信道 → feed → 新窗格 stdin`。
注意第 8/23 条的 `\x22` 就是那对双引号 —— 命令串字面量里写不出引号,转义是唯一出口。

## 9. 错误与拒绝

| 情形 | 应答 | 说明 |
| --- | --- | --- |
| 未授权 | **无** | 当作未知 OSC 号码忽略 |
| 载荷 > 4096 | **无** | OSC 段整体作废(早于本协议) |
| 命令串 > 512 | `>err;请求过长` | 信道层拒收 |
| 首字节 `>` | 无 | 回声/非请求,丢弃 |
| 未知命令 | `>err;未知命令: xxx` | 解释器给的语法错 |
| 词法/参数错 | `>err;<原因>(用法: …)` | 解释器给的用法错 |
| 执行失败 | `>err;执行失败` | 命令返回 false 且无原因时兜底 |
| 壳层失败(池满等) | 无(当前不可达) | 见 §11 |

**`err` 的 body 必非空**:`command` 层保证失败时至少写入一条兜底原因。

**回写为什么挂在 `UpdateConsole` 最前,而且无条件跑**:

```odin
UpdateConsole :: proc(console_h : mem.Handle) {
	oscCmdReap(console_h)   // ← 必须在所有早退之前,且对**无会话** console 也要跑
	console := GetConsole(console_h)
	if console == nil { return }
	...
}
```

两个理由:

1. 该函数在"无输出/无会话"时会早退,回写挂在尾部会被整趟跳掉。
2. **无会话 console 的 poll 也必须排空** —— 否则 `read_head` 永远追不上 `head`,
   阻塞式主循环的 `CommandPipePending()` 会恒为真,**主循环永远无法入睡**。
   (`ConsoleUpdateTree` 因此对无会话 console 也调 `UpdateConsole`,只是在其中跳过拉取输出。)

## 11. 不变式清单(可断言)

1. `ret_status == .None` ⟹ `ret_len == 0`
2. `ret_status == .Err` ⟹ `ret_len > 0`
3. `OscCmdEncode` 的输出**每个字节** ∈ `0x20-0x7E ∪ 0x80-0xFF`
4. `OscCmdEncode` 的输出总以 `>ok;` 或 `>err;` 开头,且至少含 3 段
5. `Console.poll_h.id != 0` ⟺ 该窗格已授权
6. 未授权时 `OSC 999` 不产生任何可观察效果(不执行、不入队、不回复)
7. 授权只在 `consoleInitSession` / `consoleClearSession` / `DestroyConsole` 三处释放
8. `PushCommand` 失败只有两种原因:句柄失效、命令串超长(均不静默:超长有 `err` 应答)
9. `UnescapeArg`(feed 参数转义)对未知转义**原样保留**;输出装不下时返回 `false`
   —— 它是"命令串 → 真实按键"的翻译表,错了就是往用户 shell 里打错键

> 当前 `oscCmdRequest` 里 `PushCommand` 失败的 `>err;信道忙` 分支**不可达**
> (poll 是动态数组,不设容量上限;句柄刚查过;长度刚查过)。保留它是防御,
> 不是现状描述 —— 若将来给 poll 加容量上限,它会立刻变成可达路径。
